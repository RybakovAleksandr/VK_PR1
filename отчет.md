## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Рыбаков Александр Даниилович |
| Вариант (запрос) | Q3 (Shipping Priority) |
| Масштаб `sfN` | sf5 |
| Почему выбрал такой масштаб | sf5 — это 30 млн строк `lineitem` и 7,5 млн заказов, около 1 ГБ сжатого Bronze. На таком объёме уже хорошо видна разница между кодеками по размеру (943 МБ у GZIP против 2500 МБ без сжатия) и по времени записи (37 с против 17 с). При этом всё помещается в память ноутбука (30 ГБ RAM): весь Bronze пишется за 25 с, а пять вариантов бенчмарка — за пару минут. На sf1 разница тонет в накладных расходах, а sf10 я уже прогонял в гайде 3: там одна таблица занимает до 4,3 ГБ, и пять вариантов × 3 таблицы заняли бы лишнее время и диск. Кроме того, sf5 — тот же масштаб, что в laba2 (`materialize_sf5.sql`), поэтому цифры можно сравнивать. |

## 2. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Образ `pgsty/silo:RELEASE.2026-09-16` — свободный форк MinIO: тот же бинарник и API. Он реализует S3 API, поэтому Trino, Spark и Lakekeeper работают с ним как с AWS S3, и стек без изменений переносится в облако. В отличие от HDFS, это один контейнер без кластера. Хранилище отделено от вычислений: данные лежат один раз, а читать их может любой движок. Официальный `minio/minio` больше не раздаётся бесплатно, поэтому взят форк. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | `postgres:17` — единственный бэкенд, который поддерживает Lakekeeper. Это надёжная транзакционная БД: коммит таблицы Iceberg — это атомарная замена указателя на metadata.json, и делать это нужно в ACID-хранилище. Порт наружу не открыт, база нужна только Lakekeeper внутри сети. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | `quay.io/lakekeeper/catalog:v0.13.6`. Реализует открытый Iceberg REST API, поэтому одни и те же таблицы видят и Trino, и Spark (проверено в п. 6.2). Hive Metastore тяжелее (Java + Thrift) и не умеет REST, а Nessie и Polaris сложнее в настройке. Lakekeeper — один лёгкий бинарник на Rust. Warehouse на каждый слой (bronze/silver/gold/bench) изолирует слои по бакетам. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | `trinodb/trino:476`. Распределённый MPP-движок для интерактивного SQL, хорошо поддерживает Iceberg: CTAS с выбором формата и кодека, `$files`/`$snapshots`, time travel, `rollback_to_snapshot`, schema evolution. В отличие от Spark, у него нет «налога на старт» JVM: Gold-запрос выполняется за 0,03–0,08 с против 2–3 с в Spark (п. 6.2). Коннектор `tpch` генерирует исходные данные любого масштаба без отдельной загрузки. |
| (BI: Superset / Metabase) | отчёт/дашборд поверх Gold | Не поднимал. Для п. 6.2 вместо BI выбран движок Spark (см. строку ниже и п. 6.2). Gold-витрина `gold.tpch.q3_unshipped_orders` уже готова для BI: одна таблица без джойнов, сегмент выбирается фильтром. |
| Spark | Второй движок поверх тех же таблиц (п. 6.2 и параллельный прогон Gold-запроса) | `apache/spark:3.5.9-java17` + Iceberg 1.12.0. Нужен для пакетных задач: читает те же Iceberg-таблицы через тот же Lakekeeper без экспорта. Запускается с `--rm` только на время задачи и не держит ресурсы. Jar'ы Iceberg 1.7.1 из laba2 с этим образом падают с SIGSEGV, поэтому взят 1.12.0. |

> Если поднимал что-то ещё (или вместо чего-то) — допиши строку. В «Почему именно он» пиши не «так было в гайде», а что даёт этот выбор: открытый исходный код, S3-совместимость, коннекторы, скорость, дешевизна и т.д.

### Скрипты, которыми поднимал стек

Вставь свои команды (`docker run` / `docker-compose.yml` / shell-скрипт), которыми реально поднял сервисы, с кратким комментарием к каждой.

Полный скрипт — [`stack/start-stack.sh`](stack/start-stack.sh), файлы каталогов Trino — [`stack/catalog/`](stack/catalog/).

```bash
docker network create lakehouse          # общая сеть: контейнеры видят друг друга по имени

# MinIO (форк Silo) — объектное хранилище; порты только на 127.0.0.1
docker run -d --name lakehouse-minio --network lakehouse \
  -p 127.0.0.1:9000:9000 -p 127.0.0.1:9001:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  -v minio-data:/data \
  docker.io/pgsty/silo:RELEASE.2026-09-16T00-00-00Z server /data --console-address ":9001"

# бакеты под слои медальона и под бенчмарк
docker run --rm --network lakehouse --entrypoint /bin/sh \
  docker.io/pgsty/mc:RELEASE.2026-09-16T00-00-00Z \
  -c "mc alias set m http://lakehouse-minio:9000 minioadmin minioadmin && \
      for b in warehouse bronze silver gold bench; do mc mb --ignore-existing m/\$b; done"

# PostgreSQL — метаданные Lakekeeper (порт наружу не нужен)
docker run -d --name lakehouse-pg --network lakehouse \
  -e POSTGRES_PASSWORD=postgres -v pg-data:/var/lib/postgresql/data \
  docker.io/library/postgres:17

# Lakekeeper — миграции БД, затем сам Iceberg REST Catalog на :8181
docker run --rm --network lakehouse \
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@lakehouse-pg:5432/postgres' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@lakehouse-pg:5432/postgres' \
  quay.io/lakekeeper/catalog:v0.13.6 migrate
docker run -d --name lakekeeper --network lakehouse \
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@lakehouse-pg:5432/postgres' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@lakehouse-pg:5432/postgres' \
  -p 127.0.0.1:8181:8181 quay.io/lakekeeper/catalog:v0.13.6 serve

# принять ToU и зарегистрировать warehouse bronze/silver/gold/bench
# (remote-signing выключен — иначе Spark получает 403 от MinIO)
curl -X POST http://localhost:8181/management/v1/bootstrap \
  -H "Content-Type: application/json" -d '{"accept-terms-of-use": true}'
for wh in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse -H "Content-Type: application/json" \
    -d '{"warehouse-name":"'$wh'","project-id":"00000000-0000-0000-0000-000000000000",
         "storage-profile":{"type":"s3","bucket":"'$wh'","key-prefix":"","endpoint":"http://lakehouse-minio:9000",
           "region":"us-east-1","path-style-access":true,"flavor":"s3-compat","sts-enabled":false,
           "remote-signing-enabled":false},
         "storage-credential":{"type":"s3","credential-type":"access-key",
           "access-key-id":"minioadmin","secret-access-key":"minioadmin"}}'
done

# Trino — SQL-движок; каталоги bronze/silver/gold/bench (Iceberg REST) и tpch из папки catalog/
docker run -d --name trino --network lakehouse \
  -p 127.0.0.1:8080:8080 \
  -v "$(pwd)/catalog:/etc/trino/catalog:ro,Z" \
  docker.io/trinodb/trino:476
```

`docker ps` на момент сдачи:

```
lakehouse-minio   pgsty/silo:RELEASE.2026-09-16T00-00-00Z   Up
trino             trinodb/trino:476                          Up (healthy)
lakekeeper        quay.io/lakekeeper/catalog:v0.13.6         Up
lakehouse-pg      postgres:17                                Up
```

|---|---|---|
| customer | `c_custkey`, `c_mktsegment` | `c_mktsegment = 'BUILDING'` — фильтр по сегменту; `c_custkey = o_custkey` — джойн с orders |
| orders | `o_orderkey`, `o_custkey`, `o_orderdate`, `o_shippriority` | `o_orderdate < 1995-03-15` — фильтр (заказ сделан до даты); `o_custkey` / `o_orderkey` — джойны; `o_orderdate`, `o_shippriority` — группировка, вывод и сортировка (`ORDER BY revenue DESC, o_orderdate`) |
| lineitem | `l_orderkey`, `l_extendedprice`, `l_discount`, `l_shipdate` | `l_shipdate > 1995-03-15` — фильтр (позиция ещё не отгружена); `l_orderkey = o_orderkey` — джойн, группировка и вывод; `sum(l_extendedprice * (1 - l_discount))` — агрегат `revenue` |

## 5. Тесты производительности

Прогони свой запрос и замерь, сколько он выполняется. Затем пересоздай Bronze с разным сжатием и сравни, как кодек влияет на время запроса и размер данных.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | 1,225 с — первый прогон; 1,066 с — медиана прогонов 2–5. Запись 3 таблиц: 36,9 с | 943,5 | Самый компактный (на 2,5 % меньше ZSTD), но запись в 2,2 раза дольше (36,9 против 17,1 с), а Q3 на ~28 % медленнее (1,07 против 0,83 с): распаковка GZIP тяжелее для CPU. Подходит для холодного архива, который пишут один раз и почти не читают. |
| ZSTD | 0,937 с — первый прогон; 0,834 с — медиана прогонов 2–5. Запись 3 таблиц: 17,1 с | 967,8 | **Лучший баланс, выбран для всех слоёв.** Размер почти как у GZIP (+24 МБ), а пишется и читается почти как без сжатия (запись 17,1 против 17,0 с у NONE; Q3 0,83 против 0,76 с у NONE). При этом данных в 2,6 раза меньше, чем без сжатия: дешевле хранить в S3 и меньше трафика из MinIO. |

> Время запроса удобно смотреть в логах Trino (`docker logs trino`) или через `system.runtime.queries`.

Как мерил ([`sql/04_codec_bench.sh`](sql/04_codec_bench.sh), сырые данные — [`bench/`](bench/)). Три таблицы Q3 (customer, orders, lineitem) пересоздаются из Bronze в схемах `bronze.bench_<формат>_<кодек>`. Кодек задаётся через `SET SESSION bronze.compression_codec`. Время берётся из `system.runtime.queries` (`end − started`). Перед чтением Trino перезапускается, затем делаются 2 прогревочных Q3 по основному Bronze (другие файлы), чтобы первый вариант не платил за прогрев JVM. Каждый запрос гоняется 5 раз. Дополнительно, для полноты, — остальные кодеки и ORC ([`bench/summary.csv`](bench/summary.csv)):

| Вариант | Размер, МБ | Запись, с | Q3 1-й / медиана, с | Q1-агрегация по lineitem, медиана, с |
|---|---|---|---|---|
| PARQUET GZIP | 943,5 | 36,92 | 1,225 / 1,066 | 0,384 |
| PARQUET ZSTD | 967,8 | 17,14 | 0,937 / 0,834 | 0,254 |
| PARQUET SNAPPY | 1332,8 | 16,89 | 1,003 / 0,883 | 0,267 |
| PARQUET NONE | 2500,2 | 17,02 | 0,797 / 0,760 | 0,215 |
| ORC ZSTD | 993,5 | 17,41 | 1,016 / 0,863 | 0,487 |

Замечания. На локальной машине сеть до MinIO бесплатная, поэтому NONE читается быстрее всех. В облачном S3, где платишь за объём и упираешься в пропускную способность, выгоднее сжатие. Разброс между прогонами — около ±0,1 с, поэтому разница ZSTD/SNAPPY/ORC в Q3 в пределах шума. Устойчивы три вывода: GZIP медленнее всех и в записи, и в чтении; NONE в 2,6 раза больше; ORC в Trino на Q1 почти вдвое медленнее Parquet.

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная OLTP-БД (Postgres) хранит данные построчно на одном сервере: аналитический запрос по 30 млн строк читает все колонки и упирается в один диск и CPU, а рост объёма означает покупку более мощного сервера. Классическое DWH решает аналитику, но данные заперты в проприетарном формате и движке, и хранение там дорогое. Lakehouse разделяет хранение и вычисления. Данные лежат дёшево в объектном хранилище (S3/MinIO) в открытом колоночном формате (Parquet), а Iceberg добавляет поверх файлов то, что было только у БД: ACID-коммиты, схему, снапшоты, time travel, эволюцию схемы и партиций. Поэтому один набор данных одновременно читают Trino (интерактивный SQL) и Spark (батчи, ML) — у меня оба читали `bronze.tpch.lineitem` без копирования (п. 6.2). Масштабируются они независимо: место — добавлением бакетов, скорость — добавлением воркеров. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Скрипт [`sql/05_evolution_timetravel.sql`](sql/05_evolution_timetravel.sql), на копии `silver.tpch.customer_evo` (750 000 строк). **ADD COLUMN** `c_vip boolean`: операция мгновенная, файлы не переписывались. После `INSERT` 725 новых строк с `c_vip = true` запрос `GROUP BY c_vip` показал: `true → 725`, `NULL → 750 000` — у старых строк колонки физически нет, и Iceberg возвращает NULL. **RENAME COLUMN** `c_acctbal → c_account_balance`: старые данные сразу читаются под новым именем (`1 → 711.56`, `2 → 121.65`, …), потому что Iceberg хранит колонку по числовому ID, а имя — лишь метка в metadata.json. Изменения схемы снапшотов не создают: в `$snapshots` только `append` (CREATE), `append` (INSERT) и `delete`. |
| Пример скрипта восстановления данных из снапшота (time travel) | [`sql/06_restore_snapshot.sh`](sql/06_restore_snapshot.sh). Сценарий «авария»: `DELETE … WHERE c_mktsegment='BUILDING'` удалил 150 442 строки (750 725 → 600 283). Скрипт берёт предпоследний снапшот (до delete) и делает следующее: <br>1) смотрит, что вернём (только чтение): `SELECT count(*) FROM silver.tpch.customer_evo FOR VERSION AS OF 5890840682668349932` → 750 725 строк, BUILDING = 150 442; <br>2) откатывает: `ALTER TABLE silver.tpch.customer_evo EXECUTE rollback_to_snapshot(5890840682668349932)`; <br>3) проверяет: после отката 750 725 строк, BUILDING = 150 442, а в `$history` снапшот delete помечен `is_current_ancestor = false`. Данные не копировались: Iceberg просто перевёл указатель текущего снапшота на старый, а файлы удаления стали неактуальны. |

### 6.2. Подключить инструмент к lakehouse

Подними в Docker **один** инструмент, который умеет работать с lakehouse, и покажи его взаимодействие с данными на **Bronze**-слое. Выбери из:

- **BI** — например Superset / Metabase;
- **движок** — например Doris / StarRocks / Spark (и обоснуй, какой лучше для твоей задачи);
- **дата-каталог**.

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Spark 3.5.9 (`apache/spark:3.5.9-java17`) + Iceberg 1.12.0 | Spark подключается к тому же Iceberg REST-каталогу (Lakekeeper), что и Trino, и читает те же файлы в MinIO — никакого экспорта, это и демонстрирует открытость lakehouse. Для моей задачи (ELT медальона) Spark — стандартный инструмент тяжёлых батч-преобразований: он умеет spill на диск и делать retries, и долгие ETL-джобы в проде обычно гоняют на нём. Trino же лучше для интерактивных запросов: на Gold-запросе он в 30–60 раз быстрее (п. ниже). Doris и StarRocks — отдельные MPP-СУБД со своим хранилищем: для чтения Iceberg им нужен external catalog, и они тяжелее для ноутбука (FE + BE). Spark же запускается одним `docker run --rm` только на время задачи. |

## 7. Выводы

Кратко, 3–5 предложений: что понял про медальон, хранение и сжатие, чем твой выбор лучше альтернатив.

Медальон разделяет ответственность. Bronze — неизменная копия источника, из которой всегда можно пересчитать слои выше. Silver — очищенные, нормализованные и обогащённые данные, где отброшены ненужные колонки (lineitem 745 → 437 МБ). Gold — маленькая готовая витрина под бизнес-вопрос (2,9 МБ, 283 856 строк), на которой Q3 выполняется за 0,03–0,08 с вместо ~0,85 с по сырому Bronze и без джойнов. Бенчмарк показал, что кодек — это компромисс «размер ↔ скорость». GZIP самый компактный (943 МБ), но пишется в 2,2 раза дольше и читается на ~28 % медленнее. NONE самый быстрый локально, но в 2,6 раза больше (2,5 ГБ). ZSTD почти так же компактен, как GZIP, и почти так же быстр, как NONE, поэтому выбран для всех слоёв. Партиционирование по колонкам фильтра (`year(o_orderdate)`, `year(l_shipdate)`, `c_mktsegment`) позволяет не читать лишние файлы. Iceberg-снапшоты дали восстановление после ошибочного DELETE одной командой `rollback_to_snapshot`, без копирования данных.
